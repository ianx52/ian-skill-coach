# 工序 · 八道工序与四道门（逐步操作）

> `SKILL.md` 里有那张总表。这份是**逐步操作**：每道工序**具体做什么、产出什么、怎么验**。
> 按需要跳读，不必顺序读。

---

## 全流程一览

```
S0 澄清 ──→ S1 对标 ──→ S2 起草 ──→ S3 触发门 ──→ S4 对照验收 ──→ S5 可移植 ──→ S6 安全 ──→ S7 打包
                            ↑           │            │              │            │
                            └───────────┴────────────┴──────────────┴────────────┘
                                    任一门 FAIL → 退回 S2 重写，不打补丁
```

**四道门 = S3 / S4 / S5 / S6**。S8（工业级）是横切评审，随时可跑。

---

## S0 · 澄清与形态决策

**做什么**：把模糊需求变成确定的需求说明，并给出形态建议。
**产出**：需求说明（六到七问的答案）+ 形态结论（纯 Skill / Agent-in-Skill / 原生 Agent 增强）。

**操作**：

```bash
python3 scripts/skillcoach.py --intake
```

**两个容易做错的地方**：

1. **把「答不清」当成「劝退」**。答不清正是需要你的理由——帮他把话问出来，
   而不是说「你想清楚再来」。
2. **跳过第四问**。前三问决定「做成什么」，第四问决定「**值不值得做**」——
   而「成功做出来一个没用的东西」是最贵的失败：**它看起来像成功**。

**停止条件**：客户说不出「你会怎么跟它说」那第一句话 → **停在这里，别往下走**。
后面所有工序都建立在 description 上，这句写不出来，做出来也不会被触发。

---

## S1 · 对标与升级策略

**做什么**：先看别人做到哪了，再定「从哪一维超越」。
**产出**：升级策略表（**给委托方看，不进交付包**）。

**操作顺序**：① 本地已装 → ② 公开仓库 → ③ 官方规范。三层都找完再下结论。

**⚠️ 重点找「上位」，不是「同类」**：

| | 是什么 | 找到的价值 |
|---|---|---|
| **同类** | 做同一件事的同水平者 | **打平**——你还是没有理由被选中 |
| **上位** | 把这类事做到极致的人，**可能根本不在同一品类里** | 能借他的做法，形成**维度上的超越** |

**升级四步**：拆维度 → **只选 1–2 维超越**（全都要超越 = 全都超越不了）→
补它没覆盖的场景 → 对照验证。

**硬判据**：找不出可以赢的维度 → 劝退。
注意措辞——**不是「找不到同类就别做」，是「找不到能赢的地方就别做」**。

**⚠️ 对标样本先看日期**：拿到任何材料，**第一步是看日期**。
超过 6 个月的做法，结论一律标注「**基于旧样本**」并降低置信度；
**引用时必须写明时间**——不给日期的引用等于不可核查。

---

## S2 · 起草

**产出**：`SKILL.md` + `references/` + `scripts/`。

**起草顺序（按 C 系列判据排的，别调）**：

1. **先写 description 的四问**（C1）——写不出「何时不用」，说明边界没想清，回 S0
2. **再排三层**（C2）——先决定什么进正文、什么下沉 `references/`，再动笔
3. **然后写正文**，关键约束放两端（C3）
4. **每条硬规则补齐四要素**（C4）——特别是「验证方式」
5. **通读找动态内容**（C5）
6. **补来源与版本声明**（C6）
7. **最后写完成定义**（V4）与「什么算成功」（V1）

**为什么先写 description**：它是唯一的触发依据。结构写完了才发现 description 写不出边界，
就要回头重来——**前面的活白干**。

**反借口段**：正文 ≥ 80 行必填。写法见 `03-反借口段写法.md`。

**第 8 招最容易漏的一项**：description 里要有**具名理论锚定**——
「AIDA 模型」「金字塔原理」「STAR 法则」这类有名字的框架不是装饰，
是给 agent 的**推理依据**。有名字，它才能推「为什么」；没有，只能机械照做。

## S3 · 触发门（第一道）

**判据 Q1**：该响应时响应、不该响应时闭嘴。

**做什么**：准备两组话术——
- **正样本** 5+ 条：用户真会说的、**应该**触发这个 skill 的话
- **负样本** 3+ 条：沾边但**不该**触发的话

```bash
python3 scripts/skillcoach.py --triggers <目录>
```

**⚠️ 脚本只能提候选，判不了「该不该触发」。** 负样本必须人工构造、逐条核对。

**为什么这道门排第一**：它是**唯一一道失败后完全无声**的门。
内容错了用户会告诉你；**装上去不触发，用户不会说——他只会不用**。

**常见错法**：
- 只写正样本，没写负样本 → 门形同虚设
- 负样本写得太远（「今天天气怎么样」）→ 任何 skill 都能过，测不出区分度
  正解：负样本要写**沾边但不该触发**的，比如同领域但不同任务

## S4 · 对照验收（第二道）

**判据 Q2**：有它比没它明显更好？

**做法**：
1. 准备一组真实任务（`tests/eval.json` 之类）
2. **同一批任务跑两次**：一次带 skill，一次不带
3. 由**不是作者本人**的人/agent 盲评

**⚠️ 铁律：改的人与评的人不能是同一个。** 作者评自己的作品，只会评出「符合预期」。
评审包必须**不含任何作者意图**（不写「这里我特意…」）。

**判据不是分数，是「差点被说服的地方」**：那些对方觉得没问题、
但你事后发现错了的地方——**那才是真正的收获**。

**单维度否决**：只要有一维（比如「无副作用」）不合格，总分再高也不通过。

**什么时候算完成**：说清楚「改完之后哪一件事变了」。说不出，就是没测。

---

## S5 · 可移植门（第三道）

**判据 Q3**：换一家工具会不会悄悄残废？

**做什么**：列出全部的路径依赖与能力依赖，逐条标注「这家支持 / 那家不支持」。

- **路径**：脚本用相对路径还是绝对路径？工具的工作目录是哪个？
- **能力**：递归读文件？执行 shell？联网？这些不是所有 harness 都有。
- **目录约定**：`agents/` 这类目录**不是任何开放标准**。
- ⚠️ **字段**：**frontmatter 字段名各家不同，而且会直接冲突**。
  实测过一例：同一个包，某平台要求的 `slug / displayName / version / summary`，
  在官方 spec 校验器里被判为「**意外字段**」——
  它只允许 `name / description / license / compatibility / metadata / allowed-tools`。
  **一个包不可能同时最合规于两边**，只能**按目标平台取字段**（或出两版）。
  <br>⇒ 这一条比路径冲突更隐蔽：**路径错了会报错，字段多了不会报错，只会被静默拒绝或判不合规。**

**分层原则**：核心逻辑写进 `SKILL.md` + `references/`（基线层，跨工具通用）；
平台专属能力只作**增强层**，换一家掉回基线层而不是残废。

**⚠️ 常见错法**：在核心逻辑里直接调用某家专有的目录或字段——换一家就整个不能用。

## S6 · 安全门（第四道）

**判据 Q4**：会不会读凭据、外发数据、跑危险命令？

```bash
python3 scripts/skillcoach.py --security <目录>
```

**扫什么**：明文凭据 / 危险删除 / 管道执行远端脚本 / 绝对用户路径 / 外发数据。

**⚠️ 脚本只覆盖结构性模式。** 判不了「这段逻辑本身危不危险」——那要人工通读。

**红线**：股票 / 彩票 / 医疗 / 法律只做数据不做决策。

---

## S7 · 打包交付

**判据 Q5 装得上 / Q6 说得清**。

**装得上**：「装了不生效」是退货第一大原因。交付包里必须有：
安装路径、触发方式（是自动触发还是斜杠命令）、以及**多数工具只在启动时扫描技能目录**这条提醒。

**说得清**：包内必须有 README（这是什么、怎么装、怎么用、不适用什么）。

**⚠️ 门不过不许打包**。门不过还打包，等于把返工成本转给使用者。

---

## S8 · 工业级就绪评审（横切）

**判据 I1–I6，按复利性排序**。详见 `SKILL.md` 的表。

**为什么只看三条 Critical（I2/I5/I4）**：

> **它们的失败会「静默复利」**——没测试 → 越改越烂；边界模糊 → 越用越偏；没版本 → 坏了没法回退。
> **共同特征：不做也不坏，所以正常节奏里没人做。**

**⚠️ 铁律**：**做不出来就说做不出来**——标「**本项不适用，原因是 X**」，
**不许写「已检查」糊过去**。

**「没查」和「查过没问题」必须产出不同的结果**：
前者标 `NOT_APPLICABLE`，**绝不标 `PASS`**。

---

## 改完之后

**任一验证门不通过 → 退回 S2 重写，不打补丁。**

「打补丁」为什么不行：补丁会让判据和产物**逐渐脱钩**——
判据说的是 A，产物做的是 B，而门还在按 A 检查，于是**门开始撒谎**。

改完跑一遍：

```bash
python3 scripts/skillcoach.py --diagnose <目录>
python3 tests/test_skillcoach.py
```

**再跑一次的意义在于「比」**：把升级前那份结果拿出来，**逐项比等级与差异**。
不比，就只是「我觉得好多了」。

⚠️ **一次只改一两处，改完就复跑**。同时改五处——进步了不知道是谁的功劳，退步了不知道是谁的锅。
