# 判据 · Skill 凭什么有效

> 这一份回答一个问题：**「一个 Skill 凭什么有效？」**
>
> 工序（怎么造）和门（怎么验）在 `SKILL.md` 里。这一份讲**判据本身**——
> 每一条为什么成立、怎么验、什么时候会失效。
>
> 判据分两组：**C 系列（七条）** 管「会不会被用」，
> **V 系列（四条）** 管「怎么证明有用」。前者决定它值不值得装，后者决定它算不算做成了。

---

## 零、为什么 Skill 需要「上下文工程」这一层

**Skill 不是文档，是上下文包。**

这句话是整个判断的支点。写成文档，评价标准是「人读得懂吗」；
写成**上下文包**，评价标准就变成三条硬指标：

| 指标 | 含义 | 不达标会怎样 |
|---|---|---|
| **会被触发吗** | description 能不能让 agent 在该用的时候用 | 装了等于没装，且**没人知道** |
| **读得进去吗** | 正文结构 vs 模型的注意力分布 | 关键约束被忽略，行为不稳定 |
| **常驻成本多少** | 每轮对话要付多少 token | 装多了拖慢所有任务 |

这三条**都不是「写得好不好」的问题，是「有没有用」的问题**——所以它们必须可检查，而不是靠感觉。

还有一条更基本的事实：**Agent 的能力上限由它拿到什么信息决定**，而不只由模型本身决定。
一个中等模型拿到组织良好的上下文，做出的事常常胜过顶级模型在信息匮乏下的摸索。
反过来也成立：**再好的方法，装在一个不会被触发的 Skill 里，价值等于零。**

## 一、C 系列判据（七条）：会不会被用

### C1 · description 是「路由条件」，不是「功能介绍」

**这是最隐蔽也最致命的一类错**：skill 内容再好，description 写宽了，
它会在**不该触发**的时候触发，在**该触发**的时候被别的 skill 抢走——而这两种失败都**不会报错**。

**为什么**：description 不是给人看的简介，它是**调度器唯一能读到的东西**。
调度器只拿这一小段去判断「现在该不该叫它」，所以它必须**写得像判定条件**，而不是像宣传语。

**合格线**：description 必须能回答四个问题

| # | 问题 | 反例 |
|---|---|---|
| 1 | **什么时候用**（具体到场景，不是品类） | ❌「帮助写作」 ✅「给口播稿做节奏检查时用」 |
| 2 | **什么时候不用**（负向边界） | ❌ 无 ✅「不用于学术论文、不用于翻译」 |
| 3 | **交给谁**（边界外去哪） | ❌ 无 ✅「排版问题那是 `x` 的活」 |
| 4 | **典型话术**（用户真会怎么说） | ❌ 书面描述 ✅「帮我看看这个、能不能发」 |

**常见错**：只写第 1 条（大多数人只写这个），或把 4 条揉成一段散文。

**自检**：一个只读得到这一段的调度器，**能不能判断该不该叫你**？不能，就是没写到位。

---

### C2 · 三层披露结构必须成立

**结构决定成本**。三层各就各位时，一个 skill 常驻成本可能只有几十 token；
一旦把细则堆进正文，常驻/加载成本立刻翻倍，而且**稀释注意力**。

| 层 | 该放什么 | 放错的后果 |
|---|---|---|
| ① 元数据 | name + description（路由用） | 写成长文 → 常驻成本暴涨 |
| ② 正文 | 流程、判据、边界、反借口 | 堆细则 → 该按需的变成常驻 |
| ③ 细则 | 长清单、模板、案例、对照表 | 全塞正文 → 正文膨胀、注意力被稀释 |

**机制**：① 每次对话都在（常驻）；② 被触发时才整份读进来；③ 用到哪一份读哪一份。
**所以分层不是排版习惯，是成本结构。**

**可量化的自检**：正文每 100 行，至少对应 1 份 `references/`。
正文 ≥ 400 行还没有 references 的，**基本可以判定细则没下沉**。

> ⚠️ **这条是判据，不是教条**：短技能本来就不需要 references。
> 判据是「**该下沉的有没有下沉**」，不是「有没有 references」。

---

### C3 · 关键约束放在两端

**模型的注意力在上下文里不是均匀分布的**：开头和结尾分到的注意力明显更高，
**中间那一段最容易被略过**。这个现象在长上下文里尤其明显。

**这条常常被违反，而且违反得很自然**：写作者习惯把「铁律」写在最前面，把「自检」写在最后，
中间是流程——这**恰好是对的**。但一旦结构变成「背景 → 方法 → 案例 → …… → 边界」，
**边界就被埋进了中部**。

**合格线**：
- 前 20%：一句话定位 + 核心不变式 + 铁律
- 后 20%：输出前自检清单（最后一条固定是「禁止假装完成」式的收口）
- **不许把唯一一条铁律放在正文中部**

---

### C4 · 一条规则要能回答四件事

只写「不许做什么」的规则表为什么会失效：它没有边界——
agent 换个说法就绕过去了，而且**你事后无法判断它到底遵守了没有**。

一条**完整**的规则，必须能回答四个问题：

| 要素 | 回答 | 例 |
|---|---|---|
| **适用条件** | 什么时候适用 | 「**检查类任务**中」 |
| **动作** | 做什么 / 不做什么 | 「**不得**写文件」 |
| **例外** | 什么情况可以不遵守 | 「用户明说『改吧』时」 |
| **怎么验证** | **怎么知道它遵守了** | 「`git status` 无新增」 |

**最后一项是分水岭**。没有验证方式的规则，只能靠 agent 自觉；
有验证方式的规则，**可以被门抓**——而能被门抓的才叫规则，其余的只是愿望。

> 推论：**约束动机层比约束行为层更根本**。禁用词表只堵行为，堵不住「它想绕」这件事。

---

### C5 · 前缀稳定：Skill 里不许写动态内容

**机制**：上下文里**不变的部分构成前缀**，可以被缓存复用；一旦前缀变了，
它**之后的所有缓存全部作废**，模型得从头算一遍。这是延迟和成本的直接来源。

**推论（对 skill 作者）**：skill 是**静态资产**，它的价值之一正是「每次加载都字节相同」。
所以：

- ❌ 不在 `SKILL.md` 里写「当前日期」「本次会话编号」「你的用户名」这类会变的东西
- ❌ 不要求 agent 每轮重写 skill 的某一段（那等于**自己动手把缓存废掉**）
- ✅ 需要随时间变的（今天几号、上次跑到哪），作为**运行时消息追加到末尾**，不写进 skill

> ⚠️ **顺序要分清**：「追加到末尾」和「改写前面」的代价差一个数量级。
> 前者只作废最后一段，后者作废它之后的全部。

**这是一条设计约束**：它不能靠脚本自动验，但可以在评审时一眼看出。

---

### C6 · Skill 也是注入面

**你写的 skill，是别人机器上的指令。** 它和「一段文本」的区别在于:
agent 会把它的内容**当作要执行的指令**来读——所以它天然是一个**注入面**。

**两个推论**：

1. **你在写的时候**：必须**可审查**——不允许混淆结构、隐藏指令、要求 agent 忽略其他约束。
2. **你在装别人的时候**：它是**攻击面**。所以「来源 + 版本 + 内容可读」是基本要求，
   装来源不明的 skill 之前要先看内容。

**落到产出物上**：合格的 skill 应当自带「**这是什么、什么版本、什么许可**」的声明。
**不肯说清来路的 skill，本身就是可疑的。**

---

### C7 · 长正文必须补「反借口段」

**前提是一件反直觉的事：skill 的正文，是写给一个会偷懒的执行者看的。**
只写「该做什么」，它遇到成本高的步骤就会自己找理由跳过——
而且**它不会报错，会静默降级**。你看到的是「做完了」，看不到「漏了中间三步」。

**为什么单独列一条**：上面六条管的是「它会不会被用、读不读得进去」；
这一条管的是**「读进去了，它会不会照做」**——不同层的失效，药方也不同。

**合格线**：**正文 ≥80 行 → 必填**。写法三步：

1. **先写它会说的那句原话**（第一人称口语，不是书面警告）
   —— 「这个先跳过，逻辑很简单」，而不是「遇到复杂情况时应谨慎处理」
2. **当场驳倒，给具体代价**（写清哪一步会炸、返工成本落到谁头上）
3. **至少两条，覆盖不同动因** —— 省事 / 赶时间 / 自我安慰。只写一条，它换个说法继续偷懒

**为什么阈值是 80 行**：短技能没有足够长的流程可跳，硬加反而稀释正文。
超过这个长度，说明它有多个步骤，也就有了「跳一步看不出来」的空间。

**⚠️ 这一条有天然的机器可判边界**：脚本只能判**有没有这一段**，
判不了**写得好不好**——把标题改个名就能绕过。
所以它报 `WARN` 不报 `FAIL`，且必须在输出里说清自己只判了存在性。
**别把「红灯亮着」当成「已经查透了」。**

## 二、V 系列判据（四条）：怎么证明「有用」

### V1 · 过程门槛 ≠ 结果判据

**完备性（有流程、有门、有版本号）是当场可自证的，它只是入场券。**
**有效性（真的改变了决定、事后没有后悔）是事后追认的，它才是判据。**

**危害**：拿第一层当成绩，就是**评估作秀**——门禁全绿，但没人用、或用了没变化。

**为什么这条最容易自欺**：第一层**马上能拿到**，第二层**要等很久才有信号**。
所以流程一多，人就会不自觉地**用第一层的分数去代替第二层的问题**。

**落到产出物上**：任何 skill 都应说清自己属于哪一类：
- 它**怎么算成功**？（不是「跑完了」，而是「改变了什么」）
- 谁来判？（自己 / 对方 / 事后）

### V2 · 验证器是循环的瓶颈

**一个流程的质量，取决于它的验证器，不取决于它的步骤数。**

把十个步骤排得更整齐，不会让它更可靠；**换一个更硬的验证器才会**。
这也是为什么「**谁判定可以停**」比「怎么走完」更要紧——
如果判定权在模型自己手里，它迟早会判定「差不多了」。

推论：**门要是脚本，不能是散文**。散文写的门只能靠自觉，
脚本写的门能被复跑、能被回归钉住。

### V3 · 防「敷衍性修复」

**最常见的假通过方式不是「没查」，而是「把判据改成能过的样子」**——
删掉一条测试让它变绿、把阈值调宽、把「未验证」写成「已检查」。

**为什么它比漏报更坏**：漏报你是不知道；敷衍性修复**会留下一条假的证据**，
让后来的人以为这里查过了。

**落到产出物上**：验收器要能识破这几种：① 判据被悄悄放宽 ② 样本被删 ③ 「没查」被记成「通过」。
**「没查」和「查过没问题」必须产出不同的结果**（前者标 `NOT_APPLICABLE`，绝不标 `PASS`）。

**还有一层**：验收条件本身要**够精确**。
「跑通了」「差不多好了」这类条件没有边界，等于没设——
条件不精确，被验收方就会往最松的解释上靠。

### V4 · 不过早宣称完成

**三种形态**：① 活干到一半就停 ② 假成功（看起来做完了）③ 循环停不下来。

根因通常是**没有明确的「完成」定义**，于是 agent 用「我觉得差不多了」当终止条件。

**为什么「假成功」最危险**：它带着完整的形式——有产出、有流程、有版本号——
**从外面看和真成功一模一样**。

**落到产出物上**：skill 里必须有一句**可判定**的完成定义 + 明确的停止条件。
「做到足够好」不是完成定义；「三项核对全过」才是。

## 三、怎么用这张判据表

### 造新 skill 时（顺序）

```
1. 先写 description 的四个问题（C1）—— 写不出第 2/3 条，说明这个 skill 的边界还没想清
2. 再排三层（C2）—— 决定什么进正文、什么下沉 references
3. 然后写正文，关键约束放两端（C3）
4. 每条规则补齐四要素（C4）—— 特别是验证方式
5. 通读一遍找动态内容（C5）
6. 补许可与版本声明（C6）
7. 最后写「什么算成功」（V1）+ 完成定义（V4）
```

### 审已有 skill 时

- **能机器查的**：C1 的四问在不在、C2 的行数/文件数比、C3 的铁律位置、C4 的四要素完整度、C6 的声明
- **只能人工判的**：C5（要通读）、V1–V4（要理解设计意图）

> ⚠️ **别把人工项塞给脚本**。脚本判不了设计意图，硬判就会产出**看起来很客观的误报**——
> 那比不判更坏。

## 四、这套判据与「工业级判据」的关系

| 层 | 问的是 | 谁在管 |
|---|---|---|
| **本文件（C/V 系列）** | 这个 skill **会不会被用、读了有没有用** | 这份文件 |
| **工业级（I 系列）** | 这个 skill **坏不坏、能不能维护、能不能交接** | `SKILL.md` 的工业级就绪评审 |

**两者不能互相替代**：
- 只有 I 系列 → 交付了一个**结构漂亮但不会被触发**的 skill
- 只有 C/V 系列 → 交付了一个**容易被触发但一改就烂**的 skill

**先 C 后 I**：一个不会触发的 skill，工业级做得再好也没意义。
